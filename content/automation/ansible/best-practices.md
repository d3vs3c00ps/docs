# Ansible best practices

## Purpose

This is not a list of immutable Ansible principles, but development advice drawn
from several teams' scripting experience. It assumes you already know Ansible — if
not, start with [[automation/ansible/intro]].

It aims to:

- restate a few principles
- fix a framework for writing Ansible script projects, notably by specifying naming
  rules at various levels
- describe good practice in writing Ansible code

Topics covered: collections, roles, playbooks, master playbooks and projects;
idempotence; modularity; writing and style rules; documentation; unit tests; source
control.

Best practices evolve — keep this document alive.

## Naming

Generally, the names of files, variables, collections and roles are lowercase and
follow these rules:

- composed of letters and digits plus `.`, `_` and `-`
- collections specifically must match `[a-zA-Z0-9_]`
- **the language for describing actions and variables is English**

Good:

```text
projectname_install.yml
static_website_path
```

Not:

```text
Installe_projectname.yml
Chemin_Du_Site_Web_Statique
```

### Playbooks

Named after the operations they perform and the services or components they act on:

```text
projectname_apache.yml
projectname_dump_database.yml
```

Direct execution, or execution by a master playbook, is orchestrated by the tags
they expose.

### Collections

Collection names should be generic and may bring several technologies together where
that makes sense. Taking HashiCorp as the example:

```text
hashicorp
├── docs
├── module_utils
├── molecule
│   └── default
├── plugins
│   └── modules
└── roles
    ├── terraform_config
    ├── terraform_install
    ├── vault_config
    ├── vault_install
    └── vault_pki
```

### Roles

Role names may be composed of:

- the name of the service, component, hardware or function
- the action on the service
- the name of the entity maintaining the role
- the name of the software or application the role is specifically written for

Components are separated by `_`. The preferred order is:

```text
[[(app_name|domain_name)_]]component_name[_function][_action]
```

Examples:

```text
nfs_client_install
nfs_server_configure
apache_install
rhel_secure
projectname_app_front
projectname_db_mongodb
```

### Variables

- Variable names contain only digits, letters and underscore (`_`).
- They cannot begin with a digit.
- The objects and actions they name are in English.
- Variables that exist only inside a role and are **not** meant to be overridden are
  prefixed with `__`.
- Variables generated by a fragment of code and scoped to it — such as those created
  by `register` — are prefixed with `__`.

A variable name should make clear:

- which role, collection or playbook it comes from
- what its function is
- whether it comes from an external tool or component (LDAP, a database, and so on)

Preferred form:

```text
[__][(playbook|role|collection)_]name
```

| Variable scope | Example | Description |
| --- | --- | --- |
| Playbook | `postgres_username` | the postgres user for the postgres playbook |
| Play | `__apache_status_code` | capture the status code from a `uri` module call |
| Role | `__nginx_package` | the nginx package name inside the nginx role |
| Role called from a playbook | `tower_rabbitmq_username` | the rabbitmq username, passed through the Ansible Tower playbook |
| External component | `gitlab_ldap_host` | the LDAP server to interface GitLab with a directory |

See [[automation/ansible/variables#Variable precedence]] for why the `__` convention
matters — it signals "not part of the role's interface".

## Inventory

### General

An inventory contains not only the list of hosts, but their distribution into
groups and the definition of group and host variables. These can vary from one
environment to another — dev, integration, qualification, preprod, prod. You can
also have inventories for fictional environments, for instance to hold default
values.

An inventory is a directory containing:

**One or more `hosts` files** in INI or YAML format. Make it readable by a human;
do not hesitate to use **aliases**. They avoid inadvertently overloading and
overwriting host and group vars, giving better control over variable scope:

```ini
mysql-01   ansible_host=192.168.42.21
mysql-02   ansible_host=192.168.42.22
apache-01  ansible_host=w1337.example.com
apache-02  ansible_host=w1669.example.com
```

Which is more readable than:

```ini
192.168.42.21
192.168.42.22
w1337.example.com
w1669.example.com
```

**A `group_vars` directory** holding files or directories named after host groups.
Each holds variables defined for every host in that group:

```text
preprod
└── group_vars
    ├── all
    ├── group1.yml
    └── group2.yml
```

If a group's variable file grows too large, or defines variables consumed by
different roles, prefer a directory of several files:

```text
preprod
└── group_vars
    ├── all
    ├── group_1
    │   ├── vars_role_1.yml
    │   ├── vars_role_2.yml
    │   └── vars_role_3.yml
    └── group_2
```

Likewise, if the hosts file grows too large, or you need to separate host functions
clearly, split hosts across separate files. You can also separate group definitions
from host definitions.

**An optional `host_vars` directory.** A full inventory then looks like:

```text
preprod
├── group_vars
│   ├── all
│   │   └── password.vault.preprod
│   ├── group_1
│   │   ├── vars_role_1.yml
│   │   ├── vars_role_2.yml
│   │   └── vars_role_3.yml
│   └── group_2
│       ├── vars_role_4.yml
│       ├── vars_role_5.yml
│       └── vars_role_6.yml
├── groups
├── hosts
├── hosts-backend
├── hosts-batches
├── hosts-frontend
├── hosts-database
└── vaultid.preprod
```

Guidelines:

- Group your inventories in one directory, with a subdirectory per
  inventory/environment.
- If responsibilities are separated within your organisation (prod / integration /
  code), you can keep inventories in repositories separate from the Ansible code.
- Create a `default` inventory defining default values for your group variables.
- Create a `dev` inventory as a working base for building a new inventory and
  validating your code.

On secrets: `vaultid.preprod` holds the vault master key, and
`password.vault.preprod` holds the passwords encrypted with it. The master key must
be protected, but the encrypted file can safely go into Git. See
[[automation/ansible/vault]].

### Groups and host patterns

Organise hosts into groups. In playbooks you associate tasks and roles with groups,
or combinations of groups.

A group can represent an environment type (prod, qualif), an OS type (windows2016,
opensuse, rhel), a component (apache, nginx, elastic), a function (directory, proxy,
ldap_client), an application set, and so on. The same host can belong to several
groups.

Set operations are available on groups:

| Description | Pattern |
| --- | --- |
| everything | `all` |
| one host | `hostname` |
| one group | `groupname` |
| union | `groupname1:groupname2:host1:host2` |
| exclusion / subtraction | `groupname1:!host3` |
| intersection | `groupname1:&groupname2` |

Hosts that are members of **both** `postgresql` and `projectname`:

```console
$ ansible -i inv/default -i inv/qualif --list-hosts 'postgresql:&projectname'
  hosts (1):
    pg-projectname-01
```

Hosts in `postgresql` that are **not** in `projectname`:

```console
$ ansible -i inv/default -i inv/qualif --list-hosts 'postgresql:!projectname'
  hosts (1):
    pg-server-01
```

### Aggregating inventories

You can use [several inventories at once](https://docs.ansible.com/ansible/latest/inventory_guide/intro_dynamic_inventory.html)
— a dynamic inventory, a directory of group and variable definitions, and so on. Do
not deny yourself this: you can pull a host list dynamically from your CMDB and
complete it with variables appropriate to the target environment.

Given a `default` inventory holding environment-independent values, a `qual`
inventory for qualification, and an `int` inventory for integration, with `var2`
overridden for all qualification environments and `var3` overridden for `qualif01`:

| File | Content |
| --- | --- |
| `inventories/default/group_vars/all/var1` | `var1: default1` |
| `inventories/default/group_vars/all/var2` | `var2: default2` |
| `inventories/default/group_vars/all/var3` | `var3: default3` |
| `inventories/qual/group_vars/all/var2` | `var2: qualif2` |

The inventories are merged in the order given on the command line, later ones
winning.

## Roles

Create roles with `ansible-galaxy role init`, then add a Molecule scenario with
`molecule init scenario` — see [[automation/ansible/molecule]]. Molecule 6 removed
`molecule init role`. At minimum this gives you `tasks`,
`meta`, `defaults`, `vars` and `handlers`:

```text
app.role1
├── defaults
│   └── main.yml   # default values for the role's variables
├── files          # files belonging to the role
├── handlers
│   └── main.yml   # actions to perform on a state change
├── meta
│   └── main.yml   # dependency declaration and other information
├── molecule       # test management
│   └── default
│       ├── converge.yml
│       ├── molecule.yml
│       └── verify.yml
├── README.md      # the documentation
├── .gitignore     # if the role has its own repository
├── tasks
│   └── main.yml   # the tasks that "play" the role
├── templates      # templates belonging to the role
└── vars
    └── main.yml   # role-private variables
```

Delete the optional files and directories you do not use — it improves readability,
and whoever reads your code will not have to open every file to find out whether it
matters. **Never delete `meta` or its contents.** You may well end up with only
`README.md`, `tasks`, `defaults`, `molecule` and `meta`.

When a role is used, the variables in `defaults` and `vars` are consumed, and files
or templates referenced by its tasks are looked for first in the role's own `files`
and `templates` directories.

- Always define a default value for the variables your role uses.
- Document the role in `README.md`: which variables to use, with examples.
- Tag the role's tasks, at minimum with the role's name. That lets you run only that
  role's tasks when launching a playbook — useful for debugging and for replaying
  just the part you care about.

A role in itself is not tied to a particular host or group; that link is made in the
playbook when the role is used. It can be very generic or very specific:

```text
user_create
postgres_clone_db
apache_install
apache_security_config
```

**A role must have one and only one function.** If yours serves several distinct
functions, split it.

The role's entry point is `tasks/main.yml` by default.

### Differentiating actions within a role

Using a variable:

```yaml
## tasks/main.yml of the applicationXXX role
---
- name: Install application XXX
  ansible.builtin.import_tasks: installation.yml
  when: action is defined and action == "installation"

- name: Uninstall application XXX
  ansible.builtin.import_tasks: uninstallation.yml
  when: action is defined and action == "uninstallation"
```

Called from the playbook as:

```yaml
---
- hosts: appxxx
  roles:
    - role: applicationXXX
      action: "installation"
```

**Do not use tags to differentiate a role's actions**, and do not put URLs in
`meta/main.yml`.

> [!warning] `action` is a reserved name
> With `action:` as a role parameter, Ansible warns "Found variable using reserved
> name 'action'" (`action` is a task keyword). It still works, but use another name,
> such as `app_action`.

## Playbooks

Avoid mixing `roles` and `tasks` in a playbook. If you must, use `pre_tasks` and
`post_tasks` — that way you are certain of the order everything runs in. The
execution order within a play is:

1. `pre_tasks`
2. dependencies
3. `roles`
4. `tasks`
5. `post_tasks`

```yaml
- name: Install the common baseline
  hosts: all
  pre_tasks:
    - name: Print a message
      ansible.builtin.debug:
        msg: "task executed before the roles"
  roles:
    - namespace.collection.role_name
    - example.apache.apache_install
    - logrotate
  post_tasks:
    - name: Print another message
      ansible.builtin.debug:
        msg: "task executed after the roles"
```

Prefer roles. You can call the same role several times with different variable
values — think of roles as subroutines:

```yaml
## Creates the users luke, anakin and jarjar
## on every server in the pprod group
- name: Create users
  hosts: pprod
  roles:
    - role: user_create
      user_name: anakin
    - role: user_create
      user_name: luke
    - role: user_create
      user_name: jarjar
```

- **Name your plays.**
- **Name your tasks.**

### Debug and verbosity

When using the `debug` module, use the `verbosity` option. That lets you leave your
diagnostic code in place and have the messages appear only in verbose mode, at the
level you specify:

```yaml
- name: Show diagnostic detail
  ansible.builtin.debug:
    msg: "This appears only when running ansible-playbook with -vv"
    verbosity: 2
```

## Projects

A project is the set of collections, roles, playbooks, inventories and assorted
files needed to accomplish one or more complex tasks — deploying and maintaining an
application across a set of servers, for example.

A suggested structure:

```text
.
├── ansible.cfg
├── .gitignore
├── site.yml
├── app_install.yml
├── app_start.yml
├── app_stop.yml
├── app_update.yml
├── app_build.yml
├── inventories
│   ├── default
│   │   └── group_vars
│   │       ├── all
│   │       └── group1
│   │           ├── vars_role_1.yml
│   │           └── vars_role_2.yml
│   ├── dev
│   ├── qual
│   └── prod
├── playbooks
├── roles                      # roles belonging to this project
│   └── requirements.yml       # external roles and collections to import
├── plugins
│   └── filters
└── library                    # project-local modules
```

A project usually corresponds to one repository in source control, and to one
application or type of application.

### Ansible configuration

Put project-specific Ansible options in `ansible.cfg`. This can set defaults, enable
plugins that are off by default, and define search paths for roles, plugins and
modules:

```ini
[defaults]
inventory                   = inventories/default,inventories/dev
roles_path                  = roles
filter_plugins              = plugins/filters
retry_files_enabled         = False
callback_result_format      = yaml
host_key_checking           = False
gathering                   = smart
fact_caching                = jsonfile
fact_caching_connection     = /tmp/facts_cache
fact_caching_timeout        = 7200
callbacks_enabled           = timer, profile_roles, profile_tasks
display_skipped_hosts       = False
interpreter_python          = auto_silent

[inventory]
enable_plugins              = host_list, script, yaml, ini

[ssh_connection]
control_path                = %(directory)s/%%h-%%r
control_path_dir            = ~/.ansible/cp
pipelining                  = True
ssh_args                    = -o ForwardAgent=yes -o ServerAliveInterval=60 -o ControlMaster=auto -o ControlPersist=15m
```

Notes on two of those: `interpreter_python = auto_silent` discovers the right
interpreter per distribution instead of assuming a path such as `python3`. And
`ServerAliveInterval=60` is a number of seconds; OpenSSH 10.0 also accepts `60s`.

> [!warning] Settings that do not work
> Tested with ansible-core 2.22:
>
> - `inventory = a:b`: Ansible reads this as one path and finds no inventory.
>   Separate paths with a comma.
> - `stdout_callback = yaml`: the play stops, because the `yaml` callback was
>   removed from community.general. Use `callback_result_format = yaml` (see
>   [[automation/ansible/installation#Configuring Ansible]]).
> - `ssh_args` over several lines: only the first line is kept. Write it on one line.

See [[automation/ansible/installation#Configuring Ansible]].

### Dependencies

A project can have three kinds of dependency:

- collections from third-party libraries
- roles from third-party libraries
- binaries or other projects from an artifact manager

Dependency management matters: it lets you reuse established functionality instead
of rewriting code. **It is mandatory to depend on a specific version**, so that a
playbook does not become unusable when upstream changes.

Ansible dependencies install into the first writable directory named in
`roles_path`, in `ANSIBLE_ROLES_PATH`, or passed via `--roles-path` to
`ansible-galaxy`.

Without Ansible Tower — during testing, for instance — fetch dependencies manually
before running the playbook:

```bash
ansible-galaxy install -r roles/requirements.yml
ansible-galaxy collection install -r roles/requirements.yml
```

Keep imported roles out of your commits: either use two separate role directories —
one for your own roles, one for imported ones — or add the imported path to
`.gitignore`.

## General principles

### Idempotence

Idempotent means the operation has the same effect whether applied once or several
times. For Ansible, it means a playbook replayed a second time or more should
produce no changes, assuming nothing changed on the target in between.

A playbook must be runnable repeatedly without introducing inconsistency in the
system. With no errors, a second run should report zero changes. See
[[automation/ansible/playbooks#Tasks and idempotence]].

### No scripts, shell, or command line

There are many Ansible modules covering most actions. They are written to manage
state, perform the checks, and take the actions needed to reach a given state.

Scripts and command lines are hard to manage because they do not necessarily
guarantee idempotence. Achieving it means wrapping them in tests, which adds
complexity to both playbook and script.

You may nonetheless use `script`, `command` and `shell`:

- when no equivalent Ansible module exists
- when you have a library of complex scripts doing complex things and do not want to
  reinvent the wheel

If you must use a script, verify it can be called repeatedly without causing
problems. If it is not idempotent, wrap it with controls using `register`,
`changed_when`, `creates`, `removes` and so on. See
[[automation/ansible/modules#command and shell]].

### Use existing modules

When you have a particular need — create a database, create a VM in the cloud, add a
user, replace something in a file, create a partition — always check whether a
module or role already does it. There are hundreds shipped with Ansible, documented
and with usage examples.

```bash
ansible-doc -l community.vmware
```

Not `ansible-doc -l | grep vmware`: in Ansible 15.0.0, `ansible-doc -l` with no
collection crashes (see [[automation/ansible/modules#Modules]]), so list one
collection.

Rather than writing a script, write a **module**. It is not necessarily difficult,
not necessarily in Python, and it gives you a framework. Put your modules in the
project's global `library` directory, or at role level if only that role uses them.

### Modularity

Generally, split everything you can. The idea is to reuse as much of other people's
work as possible, and to be able to replay a playbook — or part of one — as quickly
and precisely as possible against a limited set of hosts.

- split by role — see [[#Roles]]
- **small playbooks**: a playbook can include other playbooks. Rather than a long
  sequence of plays in one file, prefer small specific files included by more global
  master playbooks
- small variable files
- separate inventories per environment, hosts organised into groups — see
  [[#Inventory]]
- use tags — see [[automation/ansible/playbooks#Tags]]

### Copy and paste

As in any development, avoid copy and paste. The moment you start, think of another
approach:

- Copying scripts between projects? Extract them into a separate project used by the
  others. That applies to shell, Jinja2 and anything else.
- Copying code from one script to another? Extract it into a library.
- Copying code from one role into others? Factor it into a new role called by them.
- Copying the same code within a role? Use a loop, a separate task file, variables.
- Copying values across the inventories of different environments? Make a `default`
  inventory. Ansible lets you use several inventories, overriding and merging
  variables in the order given.
- Copying values within your variables or code? Put those values in variables.

There is always a way to avoid copy and paste. Avoiding it leaves your projects,
code and data better structured, and saves maintenance time.

### .gitignore

`.gitignore` tells Git to ignore certain file types or directories — certificates,
zip files, imported roles, and binaries generated by Python, Molecule and other
tools:

```gitignore
# OS
.DS_Store
Thumbs.db

# Editors
.vscode/
.history/
*.swp

# Python
__pycache__/
*.py[cod]
.venv/
venv/

# Ansible
*.retry
roles/galaxy/
collections/
.vault_pass
*.vault

# Artifacts
*.zip
*.tar.gz
*.rpm
*.deb

# Certificates and keys
*.pem
*.key
*.crt
*.p12
*.pfx
```

### Documentation

Document your playbooks, collections, roles, variables and projects.

Documentation lives in `README.md` files, but also in comments and in the names of
your tasks.

### README.md

The README must document the purpose of your collection, role or project, and the
variables needed to run it:

- description of the project / role / collection
- description of the architecture
- prerequisites before installation
- mandatory variables
- optional variables
- a usage example

The README format is Markdown — see markdown.

### Code review

It is always good to have your code read by someone else. Make review systematic
before each commit or merge, or on a regular cadence. Review maintains good practice
and helps it evolve. Whatever your level, code review benefits you.

### Tests

Test roles with Molecule — see [[automation/ansible/molecule]]. `molecule test`
converges twice and so proves idempotence, which is the property hardest to verify
by hand.

Lint as well as test:

```bash
ansible-lint
yamllint .
```

`ansible-lint` enforces a large part of this document mechanically — task naming,
FQCN usage, `changed_when` on commands — and is worth wiring into CI.
