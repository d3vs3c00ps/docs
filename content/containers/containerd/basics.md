# containerd basics

## Installing

On most distributions it arrives as a dependency of Docker or a Kubernetes node
setup. Standalone:

```bash
# openSUSE Leap
sudo zypper install containerd

# RHEL / Rocky / Fedora — from the Docker repository
sudo dnf install containerd.io
```

The upstream static binaries plus `runc` and the CNI plugins are the other common
route, and what most Kubernetes installers use.

```bash
containerd --version
runc --version
```

## Configuration

One file, `/etc/containerd/config.toml`. Distribution packages often ship a stub that
disables everything, so generate a full default before editing:

```bash
containerd config default | sudo tee /etc/containerd/config.toml
sudo systemctl restart containerd
```

Inspect what is actually loaded, including defaults you did not write:

```bash
containerd config dump
```

> [!warning] containerd 2.x renamed the CRI sections
> The fragments below use the containerd 1.x names (`version = 2` files). containerd
> 2.x still reads such a file and migrates it on load, but `containerd config default`
> now writes `version = 3` or later (2.3 writes `version = 4`), where the same
> settings live elsewhere:
>
> | Setting | containerd 1.x (`version = 2`) | containerd 2.x |
> | --- | --- | --- |
> | `SystemdCgroup` | `plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options` | `plugins.'io.containerd.cri.v1.runtime'.containerd.runtimes.runc.options` |
> | pause image | `sandbox_image` in `plugins."io.containerd.grpc.v1.cri"` | `sandbox` in `plugins.'io.containerd.cri.v1.images'.pinned_images` |
> | `config_path` | `plugins."io.containerd.grpc.v1.cri".registry` | `plugins.'io.containerd.cri.v1.images'.registry` |
>
> `plugins.'io.containerd.grpc.v1.cri'` still exists in 2.x, but only for the
> streaming server settings. Do not paste 1.x fragments into a file generated by
> 2.x: match the file's `version`. Tested on containerd 2.3 (kind node image for
> Kubernetes 1.37).

### The cgroup driver

The single most important setting on a Kubernetes node:

```toml
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
  SystemdCgroup = true
```

> [!danger] Mismatched cgroup drivers cause failures that look like anything else
> systemd expects to own the cgroup tree (see [[containers/cgroups-v2]]). If
> containerd uses the `cgroupfs` driver while the kubelet uses `systemd`, you get two
> managers writing the same hierarchy.
>
> The symptoms are not "wrong cgroup driver". They are pods restarting under load,
> resource limits not being honoured, nodes reporting pressure that does not match
> reality, and `kubelet` logs about failing to get cgroup stats. Both must agree:
> `SystemdCgroup = true` in containerd, `cgroupDriver: systemd` in the kubelet
> configuration.
>
> On a v2 host, systemd is the only correct answer.

### Sandbox image

The kubelet's "pause" container, which holds a pod's namespaces open:

```toml
[plugins."io.containerd.grpc.v1.cri"]
  sandbox_image = "registry.k8s.io/pause:3.9"
```

A version mismatch with the kubelet leads to the image being pulled repeatedly, which
in an air-gapped environment means pods that never start. `kubeadm config images list`
shows the tag your Kubernetes version expects (`pause:3.10.2` for 1.37; `3.9` above
is only an example).

### Registry configuration

The modern form uses a directory of hosts files rather than inline TOML:

```toml
[plugins."io.containerd.grpc.v1.cri".registry]
  config_path = "/etc/containerd/certs.d"
```

```toml
# /etc/containerd/certs.d/docker.io/hosts.toml
server = "https://docker.io"

[host."https://registry-mirror.example.com"]
  capabilities = ["pull", "resolve"]
```

See [[containers/containerd/advanced]] for mirrors, authentication and private
registries.

## State on disk

| Path | Contents |
| --- | --- |
| `/var/lib/containerd/` | Images, snapshots, content store — the bulk of the data |
| `/run/containerd/` | Runtime state, sockets, shim bookkeeping |
| `/run/containerd/containerd.sock` | The gRPC API socket |
| `/etc/containerd/config.toml` | Configuration |

> [!warning] `/run/containerd/containerd.sock` is root-equivalent
> Anything that can write to that socket can start a privileged container with the
> host filesystem mounted, which is a complete host compromise. It is the containerd
> equivalent of the Docker socket, and mounting it into a container — as some CI and
> monitoring tools ask you to — hands that container the node.
>
> ```bash
> ls -l /run/containerd/containerd.sock
> # srw-rw---- 1 root root
> ```
>
> Keep it root-owned, and treat any request to mount it as a privilege escalation
> request. See [[containers/containerd/hardening]].

`/var/lib/containerd` is also where disk goes missing on a node. Images and snapshots
accumulate; see [[containers/containerd/troubleshooting]].

## Namespaces

containerd partitions everything by namespace — a completely different concept from
the [[containers/concepts|kernel namespaces]] a container runs in. These are
administrative scopes for containerd's own objects.

```bash
ctr namespaces list
# default
# k8s.io      ← Kubernetes
# moby        ← Docker
```

Almost every `ctr` command needs one:

```bash
ctr --namespace k8s.io containers list
```

Forgetting it and seeing an empty list is the most common first containerd
experience.

## Verifying it works

```bash
sudo ctr images pull docker.io/library/alpine:latest
sudo ctr run --rm -t docker.io/library/alpine:latest test sh
```

On a Kubernetes node, check through the CRI instead, since that exercises the path
the kubelet actually uses:

```bash
sudo crictl info
sudo crictl ps
```

## systemd unit

```bash
systemctl status containerd
journalctl -u containerd -f
```

Restarting is safe for running containers, because each is parented to its own shim —
see [[containers/containerd/introduction]]. That is not true of a configuration change
that alters the runtime or cgroup driver, which existing containers will not pick up.
